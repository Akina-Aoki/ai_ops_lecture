## 4. Theory questions

### a) Explain the primary purpose of Pydantic. What core problems does it solve for developers?

Pydantic's job is to take data you don't fully trust. JSON from an API, a config file, or in this course, text generated by an LLM, and turn it into a Python object whose fields you can rely on. 

It solves two problems at once: **validation** (does `price` actually contain a number, is `in_stock` actually `True`/`False`?)

**Parsing/conversion** (turning a raw dict or JSON string into real Python types, like `str`, `int`, `list`, or your own `BaseModel` classes). Without it, you'd write manual `if` checks and `try/except` blocks everywhere data enters your program. With it, you declare the shape once (as a class), and Pydantic enforces it every time, raising a clear error the moment something doesn't fit.

### b) In Pydantic, what is the key difference between using model_validate() and model_validate_json()? When would you use each one?

Both build a model instance and validate it, but they expect different input. 
- `model_validate()` takes a Python object you already have in memory, typically a `dict` (e.g. the result of `json.load()`, like `products` in exercise 1a).

- `model_validate_json()` takes a raw JSON **string** and does the JSON-parsing step for you as well, in one call. So: if you've already parsed JSON into a dict, use `model_validate()`; if you still have the raw text (e.g. straight from a file or an HTTP response body), `model_validate_json()` saves you a manual `json.loads()` step first.

### c) How can you define a field in a Pydantic model that has a specific value constraint, such as a minimum or maximum number? Give an example.

You use `Field()` with constraint keywords. We did this for `price` in exercise 1b:

```python
price: float = Field(ge=0, description="The price as a number, without currency symbol")
```

`ge=0` means "greater than or equal to 0" — a negative price gets rejected. Other common ones are `gt` (greater than), `le`/`lt` (less/less-than-or-equal), and for strings, `min_length`/`max_length`. Pydantic checks these automatically whenever the model is built, so invalid data never silently makes it into your program.

### d) Describe how Pydantic plays a role in PydanticAI agents

PydanticAI uses your Pydantic model (passed as `output_type=...`, like `JobAdSummary` or `GradingResult` in this exercise) to tell the LLM exactly what shape of answer is expected. It turns the model's fields and `Field(description=...)` text into a schema the LLM is prompted with. When the LLM replies, PydanticAI runs that reply through Pydantic validation.

If a field is missing or has the wrong type (e.g. `words_in_article` comes back as the word "many" instead of a number), PydanticAI can send the error back to the model and ask it to retry, rather than just handing you broken data. 

In short: Pydantic defines the contract, and PydanticAI enforces that contract on an inherently unreliable text generator.

### e) What is a computed field in Pydantic?

A computed field is a value that isn't supplied directly. It's derived from other fields on the model, using Python code, and exposed as if it were a normal field (via the `@computed_field` decorator on a method/property). 

It's relevant here because of exercise 0e's `words_in_article`: asking an LLM to count words is unreliable (LLMs are bad at precise counting), but if you instead had the original ad text available on the model, a computed field could calculate the real word count in Python (`len(text.split())`) and always be exactly right.

 The lesson: anything a plain Python expression can compute shouldn't be left to the LLM to guess.

### f) What are tokens in LLMs?

Tokens are the small chunks of text an LLM actually reads and generates, not quite characters, not quite whole words. A token might be a whole short word ("the"), part of a longer word ("un" + "believ" + "able"), or a punctuation mark. 

Every piece of text you send to or receive from a model (your prompt, the ad text, the model's reply) gets counted in tokens, and this matters practically: API pricing is usually per token, and every model has a maximum number of tokens it can handle at once (see "context window" below).

### g) What are few shot examples?

Few-shot examples are one or more worked examples: input paired with the desired output, that you include directly in the prompt, so the model can imitate the pattern instead of guessing from the instructions alone. We did this concretely in exercise 3g: `few_shot_example` showed one sample student text together with a filled-in `proposed_grade`/`motivation`/`improvements`, placed inside the agent's `instructions`. 

## Glossary

Fill in this table either by copying this into your own markdown file or copy it into a spreadsheet if you feel that is easier to work with.

| terminology        | explanation |
| ------------------ | ----------- |
| few shot learning  | Giving the model a few worked input/output examples in the prompt so it can copy the pattern, instead of relying only on instructions. Used in exercise 3g. |
| token              | A small chunk of text (roughly part of a word) that an LLM reads/writes; usage and pricing are measured in tokens. |
| context window     | The maximum number of tokens (prompt + instructions + reply, combined) a model can handle in one call. Go over it and the call fails or gets truncated. |
| pydantic           | A Python library for defining the shape of your data as classes, then validating and converting real data (dicts, JSON) against that shape. |
| BaseModel          | The class you inherit from to create a Pydantic model, e.g. `class JobAdSummary(BaseModel): ...`. Each `name: type` line becomes a validated field. |
| Field              | A function used to attach extra rules/metadata to a model field — constraints (`ge=0`), a `description` (which PydanticAI sends to the LLM), defaults, etc. |
| model_fields       | A class-level attribute (dict) on a `BaseModel` that describes its declared fields — their types, defaults, and constraints — useful for inspecting a model programmatically. |
| computed_field     | A decorator (`@computed_field`) that exposes a derived value (calculated from other fields, in Python) as if it were a normal model field. |
| model_validate     | A method that builds and validates a model instance from a Python object already in memory, typically a `dict`. |
| model_dump         | A method that converts a model instance back into a plain Python `dict` — the reverse of building the model. We used it in exercise 0e (`ad_info.model_dump()`). |
| type hinting       | Writing the expected type next to a variable or function signature (e.g. `price: float`, `def load_ads(data_dir: Path) -> dict[str, str]`). Python doesn't enforce it by itself, but Pydantic and your editor do use it. |
| serialization      | Converting a Python object into a storable/transmittable format, like a `dict` or a JSON string (e.g. `model_dump()`, or `json.dump`). |
| deserialization     | The reverse of serialization: turning stored data (a JSON string, a dict from a file) back into Python objects, e.g. `json.load()` or `model_validate()`. |
| prompt engineering | Deliberately shaping what you tell the model — instructions, added context, examples — to get better or more reliable output. Exercise 3 (plain prompt → with criteria → with few-shot) is a worked example of this. |
| zero-shot learning | Asking the model to do a task from instructions alone, with no worked examples included in the prompt. What exercises 0b and 3b did, before few-shot was introduced in 3g. |
| OpenRouter         | A service that provides a single API to access many different LLMs from different providers. The exercise names it, though in this project we used NVIDIA's API instead, since it's already set up and uses the same OpenAI-style interface. |
| Agent              | PydanticAI's main class: wraps a model plus instructions (and optionally an `output_type`), and gives you `.run(...)` to send it a prompt and get a reply. |
| system prompt      | The standing instructions given to a model that apply to every call, regardless of the specific input — in PydanticAI this is the `instructions=` argument to `Agent(...)`. |
| agent.run          | The (async) method that actually sends a prompt to the model and waits for the reply, e.g. `result = await agent.run(ad, model_settings={"timeout": 120})`. The reply comes back in `result.output`. |
|                    |             |
